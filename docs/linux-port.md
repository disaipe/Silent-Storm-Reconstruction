# Оценка портирования на Linux

## Общая оценка

Технически возможно, но это крупный проект, а не разовый порт. Ключевые блокеры видны из архитектурной карты (см. [architecture.md](architecture.md)):

- **Рендер:** Direct3D9 (`d3d9`, `GfxShaders`, весь `Gfx*`-слой в `Main`) — под Linux нативного D3D9 нет, нужен либо слой трансляции (DXVK/vkd3d поверх Vulkan), либо переписывание рендера на OpenGL/Vulkan.
- **Ввод:** DirectInput8 (`Input` модуль) — придётся заменить на SDL2/что-то кроссплатформенное.
- **БД:** `ADOImport` — это COM/ADO, специфичный для Windows; нужна замена на ODBC-напрямую или другой драйвер.
- **Проприетарные бинарники:** FMOD и Bink — у FMOD есть официальные Linux-версии (лицензия отдельный вопрос), у Bink (RAD Game Tools) тоже есть Linux SDK, но здесь они интегрированы через stub-`.def`-заглушки под Windows-calling convention (`__stdcall`, `_Name@bytes`) — под Linux этот механизм не работает, нужна нормальная линковка с `.so`.
- **Компилятор/сборка:** код завязан на MSVC-специфику (`/Gr` — `__fastcall` по умолчанию, PCH через `StdAfx.h`, `.def`-экспорты, `.rc`-ресурсы с MFC-заголовками) — под GCC/Clang часть этого просто не соберётся без правок.
- **Точка входа:** `WinMain`/`WinFrame` (GDI/Win32-окно) — нужен кроссплатформенный оконный слой.

### Два реалистичных пути

1. **Не портировать, а гонять под Wine/Proton** — раз игра уже реконструирована до Win32.exe, Proton скорее всего справится с DirectInput+D3D9 через встроенный DXVK практически "из коробки", и это на порядки дешевле, чем нативный порт.
2. **Нативный порт** — реалистичен только поэтапно: сначала вынести рендер за абстракцию (SDL2/GLFW + Vulkan или OpenGL), затем ввод, затем БД-слой, и параллельно чистить MSVC-специфику. Это месяцы работы, а не дни, с учётом объёма `Main` (711 файлов).

## Оценка объёма MSVC-специфичного/ассемблерного кода

### Итог: объём небольшой, но критичный по месту

Из **1372 файлов** (`.cpp`/`.h` вне `third_party`) MSVC-специфика/asm сконцентрирована буквально в горстке файлов:

| Категория | Файлов | Что это |
|---|---|---|
| **Инлайн-ассемблер (`__asm`)** | 5 (в собираемых модулях) | x86 MASM-синтаксис, **не портируется на GCC/Clang напрямую** (у них нет inline-asm с таким синтаксисом — нужен либо intrinsics, либо GNU AT&T asm) |
| **`__fastcall`** | 3 (`aiReaction.cpp`, `RPGToHit.*`) | Легко убрать — это просто calling convention, замена тривиальна |
| **`__declspec`** | 21 файл, но 41 вхождение | Почти все — `dllimport`/`dllexport` в шаблонных `StdAfx.h` каждого модуля (по одному на модуль, копипаста) — не проблема, есть портируемая замена (`__attribute__((visibility))` или просто вырезать, раз всё линкуется статически) |
| **COM/`#import`** | 3 файла: `ADOImport/BasicDB.cpp`, `DataImport/BasicDB.cpp`, `MapEdit/...` | Настоящая Windows COM-интеграция для доступа к БД через ADO — требует полной замены слоя (на ODBC/другой драйвер), не просто перекомпиляции |
| **MFC (`afx*.h`)** | 11 файлов, **все в MapEdit** | MapEdit и так не собирается в текущей конфигурации — не блокер для порта Game.exe |

### Что реально ассемблерное (и почему это не так уж и много кода, но важное место)

Инлайн-asm — это **MMX-код** (`movq`, `punpcklbw`, `emms` и т.д.), не SSE/SSE2 (проверено — `_mm_`/`__m128`-интринсиков в проекте нет вообще):

- `Misc/HPTimer.cpp` — `rdtsc` для высокоточного таймера (тривиально заменяется на `__rdtsc()`-интринсик или `std::chrono`/`clock_gettime`).
- `Main/Bound.h` — MMX-ускоренные операции над bounding box.
- `Main/2DSceneSW.cpp`, `Main/SWTexture.cpp` — **программный (software) рендерер/растеризатор** на MMX — судя по названию, это резервный/отладочный путь без GPU, не основной D3D9-рендер.
- `Main/GSceneParticles.h` — блендинг цвета частиц через MMX.

### Вывод

MSVC/asm-специфика сама по себе — **не главный блокер порта**, объём кода тривиален (десяток `__asm`-блоков, легко переписываются на GCC inline-asm или intrinsics типа `_mm_*`, благо это классический MMX, для которого есть готовые аналоги в `mmintrin.h`, кроссплатформенном заголовке). Реальные блокеры для Linux — это D3D9, DirectInput8, COM/ADO (`#import` в `ADOImport`/`DataImport` — самый серьёзный кусок, требующий архитектурной замены, а не косметики) и MFC (но он изолирован в несобираемом `MapEdit`, так что не в счёт).

Если оценивать порядок усилий именно по asm/MSVC-слою — это дни работы, а не недели. Основные недели/месяцы уйдут на замену рендера и ADO-слоя.

## Разбор этапа «Рендер»

### Что фактически есть в коде

**Расположение:** ядро — 4 файла в `Main`: `Gfx.cpp`, `GfxRender.cpp`, `GfxBuffers.cpp`/`.h` (плюс `GfxInternal.h`, `GfxBuffersInternal.h` для типов). Вся остальная часть `Gfx*`/`G*` (130 файлов) — это сцена, материалы, частицы, ландшафт, тени и т.д., которые обращаются к рендеру через эти файлы, а не напрямую к D3D9.

**Реальная площадь соприкосновения с D3D9 API — на удивление небольшая:** ~100 вызовов `pDevice->...` на весь движок, сосредоточенных в этих 4 файлах. Это `SetSamplerState`, `SetRenderState`, `SetVertexShader`/`SetPixelShader`, `CreateVertexDeclaration`, `Clear`, `BeginScene`/`EndScene`, `SetRenderTarget`/`SetDepthStencilSurface` и т.п. — стандартный D3D9-программируемый конвейер.

**Гибридный конвейер:** помимо шейдеров, есть остатки **фиксированного конвейера** (`SetFVF`, `SetLight`, `SetMaterial`) — судя по местам (`GfxRender.cpp`, `iMissionDlgUI.cpp`, `iCommonUI.cpp`), это, вероятнее всего, 2D UI-рендер (квады интерфейса), а не 3D-сцена.

**Шейдеры — главная сложность:**
- Есть DSL-файл `ShaderCompiler/GfxShaders.txt` — 75 процедур на собственном макроязыке поверх классического D3D shader assembly (`m4x4`, `mad`, `mul`, регистры `v0`/`c10`/`oPos` — синтаксис уровня SM1.1–2.0, никакого HLSL нет вообще).
- Отдельный инструмент **`ShaderCompiler`** (использует легаси `D3DX9` из DirectX SDK June 2010) компилирует этот DSL в бинарный шейдерный байт-код.
- Результат — **157 готовых шейдеров** (`SVShader`/`SPShader`), зашитых как `DWORD`-массивы прямо в исходник `Main/GfxShaders.cpp` (370 КБ!). Первый DWORD (`0xfffe0101`) — это магическое число `vs_1_1`, т.е. реально старый шейдерный байт-код, не что-то современное.
- Ключевой момент: **этот байт-код уже скомпилирован и закоммичен** — рантайму не нужен D3DX9/легаси DirectX SDK, он нужен только для *пересборки* шейдеров, если понадобится их менять. Значит рантайм сам по себе не тянет за собой легаси-SDK-зависимость.

### Варианты замены

#### Вариант A — dxvk-native (рекомендуемый путь)

[DXVK](https://github.com/doitsujin/dxvk) — слой трансляции D3D9/10/11 → Vulkan, на котором работает большинство D3D9-игр в Proton. Есть форк **dxvk-native**, который даёт тот же `IDirect3DDevice9`-совместимый C++/COM-интерфейс **нативно под Linux, без Wine** — линкуется как обычная библиотека, отдаёт своё окно через SDL2.

Почему это ложится почти идеально на эту кодовую базу:
- DXVK **потребляет уже скомпилированный D3D9 shader bytecode напрямую** — все 157 шейдеров из `GfxShaders.cpp` можно использовать **как есть**, без переписывания на GLSL/SPIR-V.
- DXVK эмулирует и фиксированный конвейер (`SetFVF`/`SetLight`/`SetMaterial`), так что UI-рендер через `iCommonUI`/`iMissionDlgUI` тоже не потребует переписывания.
- Площадь правок — те же ~100 вызовов в 4 файлах: в основном замена инициализации устройства (`Direct3DCreate9`, окно/swapchain) на dxvk-native API + пересборка под их заголовки. Логика вызовов методов интерфейса остаётся почти неизменной, т.к. dxvk-native сохраняет ABI D3D9.
- Родной `WinMain`/`WinFrame` (GDI-окно) придётся заменить на SDL2-окно — это отдельная, но небольшая работа.

**Оценка:** если абстракция реально ограничена этими 4 файлами (что похоже на правду) — это **2–4 недели** на связку рендера с dxvk-native + окно на SDL2, плюс ещё сколько-то на отладку визуальных артефактов (старый движок, недокументированное поведение). Реалистично — **1–1.5 месяца**, с учётом неизбежных сюрпризов (например, `2DSceneSW.cpp`/`SWTexture.cpp` — MMX-software-рендерер, надо убедиться, что это мёртвый/отладочный путь, а не активно используемый фолбэк без GPU).

#### Вариант B — полный нативный порт на OpenGL/Vulkan

Переписать `Gfx.cpp`/`GfxRender.cpp`/`GfxBuffers.cpp` напрямую на OpenGL или Vulkan, отказавшись от D3D9-байткода целиком.

Стоимость сильно выше:
- Все 157 precompiled-шейдеров нужно **транслировать вручную** — сам SM1.1/2.0-ассемблер довольно простой (`mov`/`mad`/`mul`/`m4x4`), так что переписать на GLSL реально, но это 157 процедур, которые нужно ещё и повторно протестировать визуально одну за другой.
- Фиксированный конвейер (`SetLight`/`SetMaterial`/`SetFVF`) в OpenGL/Vulkan придётся эмулировать самостоятельно (в D3D9 он "бесплатный", в Vulkan фиксированного конвейера нет вообще — всё через шейдеры).
- `GfxBuffers.cpp` (55 КБ) — судя по названию, слой управления вершинными/индексными буферами и `VertexDeclaration` — тоже потребует полной переработки под другую модель буферов.

**Оценка:** **3–5 месяцев** работы одного разработчика, реалистично больше с учётом отладки старого недокументированного движка. Осмысленно только если конечная цель — не просто "запустить на Linux", а полностью избавиться от D3D9-легаси.

### Сравнение

| | Вариант A: dxvk-native | Вариант B: нативный OpenGL/Vulkan |
|---|---|---|
| Переиспользование существующих 157 шейдеров | Да, без изменений | Нет, все переписать |
| Объём правок в коде | ~100 вызовов / 4 файла + окно | Те же 4 файла + буферы + 157 шейдеров + fixed-function эмуляция |
| Риск | Средний (незнакомая мультиплатформенная либа, но проверенная в бою в Proton) | Высокий (полная переработка) |
| Оценка времени | **1–1.5 месяца** | **3–5 месяцев** |

### Вывод

Портировать рендер реально, и площадь D3D9-кода намного меньше, чем можно было ожидать (не тысячи файлов, а 4 файла + байткод-блоб шейдеров). Путь через **dxvk-native** — явно предпочтительный: он превращает "переписать рендер" в "подключить слой трансляции и починить граничные случаи", вместо полной переработки 157 шейдеров и буферного слоя.

## Разбор этапа «Ввод»

### Что фактически есть в коде

**Изоляция — почти образцовая.** Весь DirectInput8-код сосредоточен в **2 файлах**: `Input/Input.cpp` (1115 строк) и `Input/Bind.cpp` (723 строки) — итого 1838 строк. Наружу модуль отдаёт чистый namespace `NInput::` (`Input.h`/`Bind.h`) — `SMessage`, `EControlType`, `InitInput`/`PumpMessages`/`GetMessage`, систему биндов (`CBind`, `Bind`/`Unbind`, `GetControlID`).

**Main использует только эту абстракцию:** 58 файлов в `Main` обращаются к `NInput::`, но при этом **прямых упоминаний DirectInput-типов вне модуля Input — ноль в коде** (4 совпадения `DIK_`/`DirectInput` в `Main` — это просто слова в комментариях, не реальные вызовы). Это значит замена DirectInput не требует трогать игровую логику, ИИ, UI и т.д. — только сам модуль `Input`.

**Что реально дергается через DirectInput8 (`Input.cpp`):**
- `DirectInput8Create` → `IDirectInput8` → `CreateDevice(GUID_SysKeyboard/GUID_SysMouse)` — клавиатура и мышь.
- `EnumDevices(DI8DEVCLASS_GAMECTRL, ...)` — джойстики/геймпады, с перебором осей (`GUID_XAxis/YAxis/ZAxis/RxAxis/RyAxis/RzAxis`), POV-хатов, слайдеров, кнопок.
- `SetCooperativeLevel`, `SetDataFormat`, `SetProperty` (`DIPROPRANGE`, `DIPROPDWORD` — диапазоны осей, мёртвая зона), `Acquire`/`Unacquire`, `Poll`, буферизованное чтение через `GetDeviceData`/`DIDEVICEOBJECTDATA`.
- Таблица `DIK_*`-скан-кодов клавиатуры (~70 констант) — прямое перечисление кодов клавиш.

**Система биндов (`Bind.cpp`) полностью абстрагирована от DirectInput** — она работает с `SMessage`/`nAction`/строковыми именами команд, а не напрямую с `DIK_`/`DIMOFS_`-константами, так что при замене устройства ввода этот файл почти не потребует изменений.

### Важный нюанс, который надо явно учесть

Имена контролов для биндинга **генерируются динамически** из строки имени устройства DirectInput плюс индекс инстанса, например `"<Имя устройства>_KEY30"`, `"<Имя устройства>_AXIS_X"` (см. `Input.cpp:975-1069`, `nameIDs[szControlName] = ...`). Это значит:
- Если бинды/раскладки клавиш где-то сохраняются на диск/в БД по этим сгенерированным именам, при переходе на другой API ввода (у которого другая нумерация устройств/инстансов) старые сохранённые бинды не совпадут 1:1.
- Не критично — это решается пересозданием дефолтных биндов при первом запуске под Linux, но стоит сразу закладывать в план, а не натыкаться на это в процессе.

### На что заменить

**SDL2** — естественный выбор, потому что модель почти 1-в-1 совпадает с тем, что уже реализовано:

| DirectInput8 (было) | SDL2 (замена) |
|---|---|
| `DirectInput8Create` + `CreateDevice(GUID_SysKeyboard)` | `SDL_Init(SDL_INIT_EVENTS)`, `SDL_GetKeyboardState()` |
| Скан-коды `DIK_*` | `SDL_Scancode` (`SDL_SCANCODE_*`) — нужна таблица соответствия `DIK_* → SDL_SCANCODE_*`, это стандартная, много раз решённая задача (готовые таблицы есть в открытых портах Wine/эмуляторов) |
| `CreateDevice(GUID_SysMouse)`, `DIMOFS_X/Y/Z` (относительные оси) | `SDL_GetRelativeMouseState()` / `SDL_MOUSEMOTION`-события |
| `EnumDevices(DI8DEVCLASS_GAMECTRL)`, оси/POV/кнопки джойстика | `SDL_GameController`/`SDL_Joystick` API — оси, хаты (`SDL_JoystickGetHat`), кнопки — прямые аналоги есть под каждую сущность |
| `DIPROPRANGE`/`DIPROPDWORD` (диапазон осей, мёртвая зона) | В SDL нет точного аналога проперти — мёртвую зону/нормализацию диапазона придётся считать вручную (несложно, пара десятков строк) |
| Буферизованный `GetDeviceData` | SDL и так работает через очередь событий (`SDL_PollEvent`) — здесь даже проще, чем DirectInput |

### Оценка

Учитывая, что:
- весь API ввода сконцентрирован в 1838 строках, в 2 файлах;
- concept-to-concept маппинг на SDL2 почти прямой (нет ничего архитектурно чуждого — ни COM-специфики, ни экзотических режимов);
- потребителей (58 файлов в `Main`) трогать не нужно вообще — они работают через уже существующую абстракцию `NInput::`;

это **самая дешёвая из крупных подсистем порта**.

**Оценка времени: 3–7 рабочих дней** на переписывание `Input.cpp` (замена DirectInput-вызовов на SDL2-эквиваленты, таблица DIK→SDL_Scancode, обработка джойстиков) + **1–2 дня** на проверку/регенерацию системы биндов и отладку у реальных устройств (клавиатура/мышь/геймпад). `Bind.cpp` почти не требует правок — он выше уровня железа.

Единственная зависимость: SDL2 нужно завести окно и цикл сообщений раньше — а его в любом случае придётся подключать для рендера (см. раздел про dxvk-native выше), так что эту подсистему логично портировать **вместе с рендером**, используя общий SDL2-слой на окно+ввод.

### Сравнение с остальными подсистемами (для контекста)

| Подсистема | Оценка | Причина |
|---|---|---|
| **Ввод** | **3–7 дней** | Изолирован, 1838 строк, прямой маппинг на SDL2 |
| БД (`ADOImport`, для Game.exe) | 2–5 дней | ADO — не рантайм-зависимость, а мёртвый код в сборке игрока (см. раздел ниже) |
| Рендер (вариант A, dxvk-native) | 1–1.5 месяца | Больше кода, зависимость от шейдерного байткода |

## Разбор этапа «БД» (ADOImport)

### Для чего вообще нужен ADOImport

Все игровые данные — характеристики оружия и юнитов, параметры ИИ, перки, диалоги, сценарии, физические константы, камеры и т.д. (48 классов `DataXXX.cpp` в `DBFormat`) — исторически велись разработчиками как строки в реляционной **базе данных** (Access `.mdb` или SQL Server, судя по `GetDBConnectionStr`: `"DRIVER=SQL Server;...DATABASE=A5GAME"` и закомментированным вариантам Jet/Access-строки подключения). `ADOImport` — это обёртка над **Microsoft ADO** (`#import "msado15.dll"`, COM) для чтения записей из такой базы: подключение (`EstablishConnection`), построчное чтение таблиц (`COLETable`), маппинг колонок в поля C++-объектов (`NDatabase::ImportField`).

### Ключевая находка: ADO нужен только офлайн-инструменту, а не самой игре

Прослеженная цепочка вызовов меняет всю оценку:

- **`NDatabase::Import()`** (реальное ADO/COM-подключение к БД) вызывается **только из `DataImport/DataImport.cpp:49`** — это отдельный консольный инструмент `DataImport.exe`. Он подключается к живой БД, вытягивает данные через ADO и **запекает их в бинарный файл** через `NDatabase::Serialize(f, CStructureSaver::WRITE)` (формат — чанки `FileIO/BasicChunk1`).
- **`Game.exe`** во всех местах, где трогает базу (`Game/Main.cpp:140`, `Main/ModManager.cpp` — загрузка основной игры и модов), вызывает **только `NDatabase::Serialize(f, CStructureSaver::READ)`**, читая уже готовый бинарный файл `game.db`. **Ни ADO, ни COM, ни SQL Server/Access в рантайме игры не задействуются вообще.**
- Как следствие, и `Import()`/`ImportField()`-методы у всех 48 классов в `DBFormat` (`DataXXX.cpp`) — это тоже часть **офлайн-конвейера импорта контента**, а не часть рантайма игрока: они вызываются только изнутри `NDatabase::Import()`, которую `Game.exe` никогда не дергает.
- Бонус: у `DataImport.exe` есть **собственная отдельная копия** `BasicDB.cpp` (711 строк, не идентична `ADOImport/BasicDB.cpp` — 963 строки) — т.е. это исторически разошедшийся форк одного и того же файла, а не общий модуль.

### Что это значит для порта Game.exe

`ADOImport/BasicDB.cpp` сейчас — один файл, где вперемешку лежат:
1. **COM/ADO-код** (~строки 1–421): `#import "msado15.dll"`, `_ConnectionPtr`, `_bstr_t`, `_variant_t`, `EstablishConnection`, `COLETable`, `CoInitialize`/`CoUninitialize` — целиком MSVC/ATL-расширения языка, которых физически нет у GCC/Clang. Этот код **не компилируется на Linux в принципе**.
2. **Платформо-нейтральная часть** (~строки 422–963): `CDBTableBase`/`CDBRecord`/`CDBTable<T>`, реестр таблиц (`AddTable`/`AddRelation`/`GetTable`), `ClearDatabaseTables`, и главное — `Serialize()`, которую реально вызывает `Game.exe`.

Поскольку в рантайме игрока задействован **только пункт 2**, стратегия порта простая:

1. **Разделить файл** на COM-часть (компилируется только под Windows-сборку `DataImport.exe`) и generic-часть (компилируется и под Linux `Game.exe`).
2. Убрать `#import`, COM-инициализацию, `EstablishConnection`/`COLETable` из Linux-сборки — они физически не нужны, раз `Import()` никогда не вызывается из `Game.exe`.
3. `ImportField`/`Import()` у классов `DBFormat` можно оставить как заглушки (или вовсе выкинуть из Linux-сборки, если линкер не потребует символов — они не вызываются нигде, кроме недостижимого пути) — компилируются, но реально не используются.
4. Формат `game.db` — бинарный чанк-файл (`FileIO/BasicChunk1`), фактически платформонезависимый на уровне x86 little-endian (что Windows x86, что Linux x86 — совпадают по эндианности и разрядности `int`/`DWORD`); риск — только возможные расхождения в паддинге структур между MSVC и GCC при сериализации сырых `struct` (если такое где-то используется вместо `CStructureSaver`-полей) — стоит проверить, но маловероятно, раз сериализация идёт через явный `operator&`/`CStructureSaver`, а не побайтовым dump'ом структуры.

### Оценка

| Задача | Оценка |
|---|---|
| **Запустить Game.exe на Linux** (убрать COM-зависимость, оставить чтение `game.db`) | **2–5 дней** — чисто механическое разделение файла + проверка, что бинарный `game.db`, собранный на Windows-стороне пайплайна, грузится побитово идентично |
| **Портировать сам `DataImport.exe`** (регенерация `game.db` из живой БД — нужно только для моддинга/пересборки контента, НЕ для игры) | **Недели** — требует полноценной замены ADO/Jet на кроссплатформенный доступ к БД (unixODBC + mdbtools для Access, либо нативный SQL Server-драйвер), это отдельная, необязательная задача |

Это самая дешёвая "крупная" подсистема из всех разобранных — куда дешевле, чем предполагалось в общей оценке выше, где ADO изначально помечен как требующий "полной замены слоя". На деле для цели «игра запускается и играется» замена вообще не нужна — ADO просто выпиливается из билда как мёртвый код.

## Разбор этапа «Звук» (FModSound)

### Что фактически есть в коде

**Изоляция — тоже очень хорошая**, по той же схеме, что и `Input`: весь FMOD-специфичный код лежит в **одном файле** `FModSound/FMSound.cpp` (930 строк), а наружу отдаётся чистая абстракция `NFMSound::` (`FMsound.h`) — `Init`/`Done`, `LoadSample2D`/`LoadSample3D`, `PlaySound`/`Play3DSound`, `PlayStream`/`SwitchStream`, `Pause`/`FadeOut`, `SetSFXMasterVolume`/`SetMusicMasterVolume`. Никаких FMOD-типов, кроме форвард-декларации `FSOUND_SAMPLE`, наружу не течёт.

**Потребителей мало и они узкие:** только 5 файлов в `Main` используют `NFMSound::` — `Sound.cpp`, `SoundEffect.cpp`, `SoundFormat.cpp`, `UIInterface.cpp` (UI-звуки) и **`GBinkPlayer.cpp`** (видеоплеер Bink делит аудио-устройство FMOD через `GetSoundAPI()` — важный побочный момент, см. ниже).

**Важная деталь: это очень старая версия FMOD.** Используемый API — классический C-интерфейс `FSOUND_*` (не современный FMOD Studio/Core API), и комментарий в `.def`-файле прямо это подтверждает: `"FMOD 3.70, the 'fmodvc' audio lib"`. Функционал, который реально используется (~40-50 отдельных вызовов):
- 2D/3D-сэмплы (`FSOUND_Sample_Load`, `FSOUND_PlaySoundEx`, `FSOUND_3D_SetAttributes`, `FSOUND_Sample_SetMinMaxDistance`) — позиционный 3D-звук с дистанционным затуханием.
- Потоковая музыка (`FSOUND_Stream_Play/Stop/SetTime/SetPosition`, кросс-фейды через `FadeOut`/`SwitchStream`).
- Слушатель (`FSOUND_3D_Listener_SetAttributes`) — позиция/ориентация камеры для 3D-звука.
- Настройка выхода (`FSOUND_SetOutput(FSOUND_OUTPUT_DSOUND/WINMM)`, `FSOUND_SetSpeakerMode`) — это уровень, завязанный на Windows-звуковые API, будет заменяться целиком.
- **`GetSoundAPI()` отдаёт `IDirectSound*`-хэндл Bink'у**, чтобы видео синхронизировало звук через то же устройство — это создаёт связь между звуковым слоем и видеоплеером, которую нужно учитывать при замене.

Как и с `fmod.dll`/`binkw32.dll` (уже разбирали в общей оценке), сама библиотека **не входит в репозиторий** — она берётся "из retail-инсталляции игры" (см. комментарий в `fmod.def`), сборка лишь генерирует заглушку-import-lib по экспортам.

### Варианты замены

#### Вариант A — раздобыть Linux-версию FMOD той же/совместимой эры

FMOD исторически был кроссплатформенным (включая Linux) даже в начале 2000-х, так что теоретически Linux-сборка FMOD 3.7 существовала. Но:
- Это **проприетарный SDK** — распространение и даже просто использование требует лицензии Firelight Technologies; для очень старой версии (2003 г.) официальные дистрибутивы, скорее всего, давно сняты с раздачи.
- Даже если раздобыть бинарник, `FSOUND_*`-API — легаси, современные версии FMOD Core API уже другие по сигнатурам — придётся либо искать именно древний Linux-бинарник 3.7 (риск: недоступен), либо переходить на актуальный FMOD Core API (а это уже сопоставимо по объёму работы с переписыванием под другую библиотеку, только с оставлением платной/лицензионной зависимости).

**Вывод:** реализуемо только при удаче с поиском исторического бинарника; предсказуемость низкая, поэтому не рекомендую как основной путь.

#### Вариант B — заменить на OpenAL Soft (рекомендуемый путь)

[OpenAL Soft](https://github.com/kcat/openal-soft) — open-source, кроссплатформенный, изначально спроектирован именно под позиционный 3D-звук (source/listener модель), что почти 1-в-1 ложится на то, что уже реализовано:

| FMOD (`FSOUND_*`) | OpenAL |
|---|---|
| `FSOUND_Sample_Load` + `FSOUND_PlaySoundEx` | `alGenBuffers`/`alBufferData` + `alGenSources`/`alSourcePlay` |
| `FSOUND_3D_SetAttributes(channel, pos, vel)` | `alSource3f(src, AL_POSITION, ...)` / `AL_VELOCITY` |
| `FSOUND_Sample_SetMinMaxDistance` | `AL_REFERENCE_DISTANCE`/`AL_MAX_DISTANCE` на источнике |
| `FSOUND_3D_Listener_SetAttributes` | `alListener3f(AL_POSITION,...)` + `alListenerfv(AL_ORIENTATION,...)` |
| `FSOUND_Stream_Play/SetPosition/SetTime` | Потоковое воспроизведение через **очередь буферов** (`alSourceQueueBuffers`/`alSourceUnqueueBuffers`) — придётся написать свой небольшой стриминг-менеджер (в FMOD это было "бесплатно") |
| `FadeOut`/`SwitchStream` (кросс-фейд) | Ручная плавная интерполяция `AL_GAIN` по таймеру — тривиально |
| `SetSFXMasterVolume`/`SetMusicMasterVolume` | Группировка через мастер-gain на шине (в OpenAL нет "шин" из коробки — считаем вручную, умножая на итоговый `AL_GAIN` каждого источника) |
| `SetSpeakerMode` (Mono/Stereo/Quad/5.1) | В OpenAL это управляется ОС/драйвером, а не приложением — код можно сделать no-op |

**Важный открытый вопрос — декодирование.** FMOD 3.x умел сам декодировать WAV/MP3/等 из переданного в память буфера (`FSOUND_LOADMEMORY`), а **OpenAL умеет проигрывать только сырой PCM** — декодер нужен отдельно. По коду не удалось однозначно определить формат звуковых ассетов (не найдено явных проверок расширений — вероятно, формат определяется по заголовку внутри `FSOUND_Sample_Load`). Если это WAV — декодирование тривиально (несколько строк, PCM почти не требует парсинга). Если сжатый формат (MP3/ADPCM/что-то проприетарное FMOD) — потребуется подключить декодер (`dr_wav`/`dr_mp3`/`stb_vorbis`/`libsndfile`, в зависимости от формата) — это стоит уточнить в первую очередь при реальном начале работ (открыть пару файлов из `res`/pkg и посмотреть заголовок).

**Особый случай — Bink.** `GetSoundAPI()` сейчас отдаёт `IDirectSound*`, чтобы Bink синхронизировал видео со звуком через общее устройство. При переходе на OpenAL этот механизм нужно будет либо убрать (среди опций Bink under Linux свой звуковой путь), либо синхронизировать по таймкоду вручную — небольшая, но отдельная задача, требует связки с портом видео (Bink здесь не разбирали).

### Оценка

Учитывая:
- изолированность (1 файл, 930 строк, 5 потребителей);
- концептуально прямой маппинг большинства вызовов на OpenAL;
- нетривиальность — только стриминг (нужно написать буферную очередь) и, возможно, декодер формата;

**Оценка времени: 3–4 недели** на переписывание `FMSound.cpp` под OpenAL Soft (сэмплы/3D-позиционирование — быстро, ~несколько дней; потоковая музыка с очередями буферов и кросс-фейдами — самая трудоёмкая часть, ~1-1.5 недели; интеграция декодера формата — от 2-3 дней до недели в зависимости от формата) + несколько дней на синхронизацию с видеоплеером Bink.

### Сравнение с остальными подсистемами

| Подсистема | Оценка | Причина |
|---|---|---|
| Ввод | 3–7 дней | Изолирован, прямой маппинг на SDL2 |
| БД (Game.exe) | 2–5 дней | ADO — мёртвый код в рантайме игрока |
| Видео (Bink → FFmpeg) | 1–2 недели (или часы, если заглушить) | Крошечная площадь кода, но нужен пиксель/аудио-конвейер |
| **Звук (OpenAL)** | **3–4 недели** | Изолирован, но стриминг+декодер добавляют работы |
| Рендер (dxvk-native) | 1–1.5 месяца | Больше кода + шейдерный байткод |

## Разбор этапа «Видео» (Bink)

### Что фактически есть в коде

**Ещё более компактная подсистема, чем звук.** Вся интеграция с Bink — это **один файл** `Main/GBinkPlayer.cpp`, всего **276 строк**. Публичный интерфейс уже абстрактный: `NGScene::IVideoPlayer` (виртуальные `Play`/`Stop`/`Pause`/`IsPlaying`/`GetCurrentFrame`/`GetLength`/`GetSize`), конкретная реализация `CBinkVideoPlayer`, фабрика `CreateVideoPlayer()`. Важная деталь архитектуры: видеоплеер **является узлом графа зависимостей, производящим `NGfx::CTexture`** (наследует `CPtrFuncBase<NGfx::CTexture>`) — то есть кадр видео просто становится текстурой, которую 2D-сцена рисует как обычный UI-элемент. Это удобно: замена декодера не требует трогать рендер вообще, только то, что кладёт пиксели в буфер текстуры.

**Используется всего в 3 местах — исключительно декоративно:**
- `iIntroScreen.cpp` — вступительный ролик (`Nival/Intro.bik`).
- `iLoading.cpp` — зацикленное видео на экране загрузки (`loading.bik`).
- `iCreditsScreen.cpp` — финальные титры (`Credits.bik`).

Никакой игровой логики или катсцен через Bink не идёт — это чисто вступление/титры/загрузочный экран. Если что-то временно не заработает идеально, это не критично для играбельности.

**Bink-функции, реально используемые (11 штук):** `BinkOpen` (из файла или из памяти), `BinkWait`/`BinkDoFrame`/`BinkNextFrame` (цикл декодирования кадра), `BinkCopyToBuffer` (копирование кадра в текстурный буфер — с fallback-путём для нестандартных по размеру кадров), `BinkGoto`, `BinkPause`, `BinkClose`, плюс звуковая синхронизация: `BinkSetVolume`, `BinkSetSoundSystem(BinkOpenDirectSound, ...)` — тут та же связка с `NFMSound::GetSoundAPI()`, что уже отмечена в разборе звука.

Как и `fmod.dll`/`msado15.dll`, `binkw32.dll` не входит в репозиторий — генерируется только заглушка-import-lib по `.def`-файлу, сама библиотека берётся из retail-установки игры.

### Варианты замены

#### Вариант A — достать Linux-версию Bink той же эры

RAD Game Tools (ныне часть Epic) действительно поддерживает Linux — но:
- Это касается **современного Bink 2** (другой API, другие имена функций), а не старого `binkw32`-формата (Bink 1, судя по `.bik`-контейнеру и `BinkOpen`/`BinkCopyToBuffer` API из этого кода).
- Bink — коммерческий SDK, лицензирование сейчас идёт через Epic, доступность для нового/индивидуального использования ограничена, а тем более для конкретно этой легаси-версии под Linux.

**Вывод:** тот же риск, что и с FMOD — недоступность лицензии/бинарника исторической версии перевешивает выгоду. Не рекомендую.

#### Вариант B — декодировать существующие `.bik`-файлы через FFmpeg (рекомендуемый путь)

Ключевая находка: **FFmpeg уже умеет декодировать легаси Bink1** — в `libavcodec` есть реверс-инженеренные (без использования RAD SDK) декодеры `binkvideo` и `binkaudio`, доступные много лет. Это значит:
- **Не нужно ничего перекодировать** — те самые `.bik`-файлы из retail-инсталляции игры (`Intro.bik`, `loading.bik`, `Credits.bik`) можно скармливать напрямую в `libavformat`/`libavcodec`.
- Юридически чище: используется открытый (LGPL/GPL, в зависимости от сборки FFmpeg) декодер, без необходимости в лицензии RAD/Epic.

**План замены `GBinkPlayer.cpp`:**
1. `avformat_open_input` + `avformat_find_stream_info` — открыть `.bik` вместо `BinkOpen`.
2. Цикл `av_read_frame` + `avcodec_send_packet`/`avcodec_receive_frame` — вместо `BinkWait`/`BinkDoFrame`/`BinkNextFrame`.
3. Bink хранит кадры в YUV — понадобится `sws_scale` (libswscale) для конвертации в формат, который ожидает `NGfx::CTextureLock` (сейчас код рассчитывает на 16/32-битный RGB-буфер) — прямая замена `BinkCopyToBuffer`.
4. Аудиодорожку декодировать через `binkaudio`-декодер FFmpeg и отдавать в звуковой слой (тот самый, что будет портирован на OpenAL — см. разбор звука) вместо `BinkSetSoundSystem(BinkOpenDirectSound, ...)`.
5. `IVideoPlayer`-интерфейс наружу не меняется — 3 файла-потребителя (`iIntroScreen`/`iLoading`/`iCreditsScreen`) не трогаем вообще.

#### Вариант C — временно заглушить видео (самый дешёвый путь для MVP)

Поскольку все 3 использования чисто декоративные, для первой играбельной Linux-сборки можно **просто исключить видео** — сделать `CreateVideoPlayer()` no-op-заглушкой (например, статичная картинка или мгновенный пропуск), не блокируя релиз ради этой второстепенной фичи. Правильный декодер (вариант B) можно добавить отдельным этапом позже.

### Оценка

| Задача | Оценка |
|---|---|
| **Вариант C: заглушка** (пропустить видео) | **Несколько часов** — тривиальный no-op плеер |
| **Вариант B: FFmpeg-декодер** для `.bik` | **1–2 недели** — вся сложность в связке декодер→текстура (конвертация YUV→RGB) и декодер→звук (привязка к OpenAL-порту), сам API FFmpeg — стандартный, много референсов |

### Сравнение с остальными подсистемами

| Подсистема | Оценка | Причина |
|---|---|---|
| Ввод | 3–7 дней | Изолирован, прямой маппинг на SDL2 |
| БД (Game.exe) | 2–5 дней | ADO — мёртвый код в рантайме игрока |
| **Видео (Bink → FFmpeg)** | **1–2 недели** (или часы, если заглушить) | Крошечная площадь кода (276 строк), но требует пиксель/аудио-конвейер |
